**Story**: US1（P1，Feature 002 硬前置） | **Capabilities**: C-01…C-04 | **Prerequisite**: —

## 这个模块回答什么问题

1. Rust 没有 GC，也不要求手写 `free`。那么"释放"这段代码**存在于哪里**，是谁写的？
2. `let b = a;` 这一行，为什么对某些类型之后 `a` 还能用、对另一些就不能？分界线是什么？
3. 为什么同一作用域里不能有两个 `&mut`？编译器**在不运行程序的情况下**凭什么知道这有问题？
4. 生命周期标注不生成任何机器码。既然如此，它到底在约束谁？
5. 大多数函数不写标注也能编译。省略规则在什么情况下会**失效**，为什么？

## 概念

### C-01 Ownership（所有权）

- **一句话定义**：每个值在任意时刻有且只有一个**所有者**（一个变量绑定）；
  所有者离开作用域时，该值被销毁。

- **底层机制**：

  这里有两件**必须分开**看的事 —— 销毁**代码**从哪来，销毁**时刻**由什么决定。

  **销毁代码**由编译器生成，叫 **drop glue**。它在源码里不存在。
  `Drop` trait 带 `#[lang = "drop"]`（`core/src/ops/drop.rs:206`），是**语言项**：
  编译器对它有内建认知，在代码生成阶段为每个需要销毁的类型合成一段递归销毁字段的代码。
  这也是 `Drop::drop` 不能手动调用的原因（`E0040`）—— 手动调用会让编译器生成的那次销毁
  变成第二次，即 double free。

  **销毁时刻**由**静态作用域**决定，不是引用计数、不是垃圾回收。
  编译器在编译期就知道每个值的作用域末尾在哪一行，于是把 drop glue 调用插在那里。
  所以"什么时候释放"这个问题在 Rust 里是**编译期**问题，在 C 里是程序员的问题，
  在 Java 里是运行期问题。三种答案对应三种代价。

  销毁顺序是**声明顺序的逆序**（后声明的先销毁）。这不是随意规定：
  后声明的值可能借用了先声明的值，逆序销毁才能保证被引用者始终活得更久。
  实验 `c01_ownership` 用一个销毁日志把这个顺序变成了可断言的序列。

  所有权**转移**（move）后，销毁责任跟着转移：值在**新所有者**的作用域末尾被销毁，
  而不是在调用点。这是"传进函数就不归我管了"的精确含义。

- **常见误解**：
  - **误解**："Rust 在作用域结束时调用 `drop()` 函数" → **实际**：调用的是编译器合成的
    drop glue，它会递归销毁所有字段；`Drop::drop` 只是其中**可选**的一环（大多数类型没有实现它）。
    → **证据**：`tests/c01_ownership.rs::drop_runs_at_scope_end` 中 `Noisy` 有 `Drop` 实现，
    而它内部的 `&DropLog` 没有；MIR 中可见 drop glue 的插入点（OBSERVATIONS §C-01 MIR 观察）。
  - **误解**："移动之后原变量的内存被回收了" → **实际**：栈空间原样留着，
    只是编译器把它标记为"已移出"，不再对它插入 drop 调用。
    → **证据**：MIR 观察中移出后的局部变量仍占有 slot，drop 调用被条件化或省略。

### C-02 Move semantics（移动语义）

- **一句话定义**：赋值、传参、返回时，非 `Copy` 类型的值发生**移动**——
  所有权转给新位置，原位置失效；`Copy` 类型则是**复制**，原位置仍可用。

- **底层机制**：

  移动在机器层面就是一次**按位拷贝**（memcpy），而且经常被优化掉。
  它和 `Copy` 的**运行期行为完全相同** —— 差别**只在编译期的簿记**：
  移动之后，编译器把源位置标记为"已移出"，此后读它是编译错误，
  作用域末尾也不再对它插入 drop glue。

  所以"移动"不是一个动作，而是一次**责任转移**的记账。真正被搬走的不是数据，是销毁义务。

  `Copy` 与 `Drop` **互斥**，理由就在这里。`Copy` 的文档明说：
  "any type implementing `Drop` can't be `Copy`"（`core/src/marker.rs:419`）。
  若一个值既能被随意复制、又有销毁行为，那么 N 份副本各自销毁一次，
  同一份资源就会被释放 N 次。互斥不是语法洁癖，是防 double free。

  `mem::replace` / `take` / `forget`（`core/src/mem/mod.rs:953 / 886 / 189`）
  是三个"绕过常规移动"的口子，各自的约束很能说明问题：

  | 函数 | 做什么 | 约束及其原因 |
  |------|-------|------------|
  | `replace(dest, src)` | 取出 `dest` 的值，放入 `src` | 无额外约束：调用方**自带**替补值 |
  | `take(dest)` | 取出 `dest` 的值，放入默认值 | 要求 `T: Default` —— 必须有替补值可放 |
  | `forget(t)` | 拿走值并**不销毁**它 | 安全函数。实现就一行 `ManuallyDrop::new(t)` |

  前两个共同体现一条原则：**原位置绝不允许留下无效状态**。
  这正是 Rust 与 C 的分野 —— C 里 `free(p)` 之后 `p` 是悬垂指针，语言不管；
  Rust 里你没法制造出那个中间状态。

  `forget` 是**安全**的，这点常让人意外。因为泄漏内存不违反内存安全：
  没人会读到无效数据。UB 与泄漏是两个不同的范畴 —— 这个区分在 US5 会反复出现。

- **常见误解**：
  - **误解**："移动会把数据搬到新的内存位置" → **实际**：可能有一次 memcpy，也可能被完全优化掉；
    语义上的关键变化只发生在编译器的簿记里。
    → **证据**：`tests/c02_move.rs::move_does_not_duplicate_drops` —— 移动后销毁总次数仍是 1。
  - **误解**："`mem::forget` 造成 UB，所以应该是 `unsafe`" → **实际**：它是安全函数；
    泄漏资源不违反内存安全。
    → **证据**：`tests/c02_move.rs::forget_suppresses_drop` 中销毁计数为 0，程序照常运行；
    源码 `core/src/mem/mod.rs:189` 的签名没有 `unsafe`。

### C-03 Borrowing（借用）

- **一句话定义**：借用是**不转移所有权**地访问一个值。
  同一时刻，要么存在任意多个不可变借用（`&T`），要么存在恰好一个可变借用（`&mut T`），
  两者不能共存。

- **底层机制**：

  这条规则在 Rust 里有**两个执行时机**，理解 C-03 的关键就是把它们对照起来看。

  | | 编译期 | 运行期 |
  |---|-------|-------|
  | 执行者 | borrow checker（`rustc_borrowck`，编译器内建） | `RefCell` 的 `BorrowCounter` |
  | 数据结构 | 全函数控制流图 + 借用区间分析 | **一个 `isize`**（`core/src/cell.rs:945`） |
  | 违规后果 | 编译失败（`E0499` / `E0502`） | **panic** |
  | 代价 | 编译时间 | 运行期一次加减 + 分支；错误推迟到线上 |

  运行期版本的编码方案简单得出人意料（`core/src/cell.rs:945-956`）：
  `0` = 无借用，**正数** = 当前不可变借用的个数，**负数** = 存在可变借用。
  整个"运行期借用检查"就是对这个整数做加减和符号判断。

  拿它和编译期版本对比，能直接量化"把检查挪到运行期"换来了什么、付出了什么：
  换来的是能表达编译器证明不了的共享模式，付出的是错误从"编译不过"变成"线上崩溃"。

  **借用的存活区间不是作用域，而是到最后一次使用为止**（NLL，non-lexical lifetimes）。
  这条常被误解 —— 一个 `&mut` 在最后一次用过之后就"结束"了，
  哪怕它的变量绑定还在作用域里。`c03_borrow` 的实验直接观察这一点。

  规则防的是什么：**在别人持有引用期间改变数据的结构**。
  C 里的经典对应是"边遍历 vector 边 push"——realloc 之后所有旧指针悬垂。
  Rust 把这类 bug 变成了编译错误。

- **常见误解**：
  - **误解**："借用一直持续到变量的作用域结束" → **实际**：NLL 让借用在**最后一次使用**后即结束。
    → **证据**：`tests/c03_borrow.rs::nll_ends_borrow_at_last_use` 编译通过本身即为证明 ——
    若借用持续到作用域末尾，那段代码不可能编译。
  - **误解**："`RefCell` 绕过了借用规则" → **实际**：它只是把**同一条**规则的检查挪到了运行期，
    规则本身一字未改。
    → **证据**：`tests/c03_borrow.rs::refcell_double_borrow_panics_at_runtime` ——
    同样的违规，编译期版本报错误码，运行期版本 panic。

- **对应实验**：[`c03_borrow`](../../experiments/m1-ownership/examples/c03_borrow.rs)
  / [tests](../../experiments/m1-ownership/tests/c03_borrow.rs)

### C-04 Lifetime（生命周期）

- **一句话定义**：生命周期是**引用有效的代码区间**。标注（`'a`）不改变任何东西的寿命，
  它只是把"这个引用的有效期不超过那个数据的有效期"这一约束**写给借用检查器看**。

- **底层机制**：

  标注是**纯编译期**的。它不生成任何机器码，编译后完全消失（生命周期擦除）。
  它的唯一作用是给借用检查器提供**它推不出来的那部分信息**。

  编译器在多数情况下能自己推，靠的是**省略规则**（lifetime elision，三条）：
  1. 每个省略的入参生命周期各得一个独立的参数；
  2. 若**恰好一个**入参生命周期，它被赋给所有省略的输出生命周期；
  3. 若有 `&self` 或 `&mut self`，`self` 的生命周期被赋给所有省略的输出。

  `fn longest(a: &str, b: &str) -> &str` 编译不过，就是因为规则 2 与 3 都不适用：
  有**两个**候选来源，规则 3 也没有 `self`。编译器此时**不猜** —— 它要求作者说明。

  这个"不猜"是设计选择而非能力不足：猜错的后果是悬垂引用，
  而两个候选之间没有任何可靠依据能分辨该选哪个。

  标注 `'a` 表达的约束是**关系**而非具体时长：`fn longest<'a>(a: &'a str, b: &'a str) -> &'a str`
  说的是"返回值的有效期不超过 `a` 与 `b` 中**较短**的那个"。
  编译器据此在每个调用点分别检查。

  `PhantomData<T>`（`core/src/marker.rs:811`）是这套机制的一个极端案例：
  定义只有一行、**没有字段**、大小为 0（文档保证，marker.rs:805），
  却能让 `Tagged<Ingress>` 与 `Tagged<Egress>` 成为两个不能互相赋值的类型。

  它证明了一件重要的事：**类型层面的区分与运行期的空间占用完全无关**。
  这是"零成本抽象"最纯粹的形态，也是后续 eBPF map 类型标注一类设计的基础形状。

- **常见误解**：
  - **误解**："`'a` 决定了引用能活多久" → **实际**：它只**描述**已经存在的约束关系。
    加标注不会让任何数据多活一纳秒；标注错了只会导致编译失败，不会导致运行期行为改变。
    → **证据**：`tests/c04_lifetime.rs::lifetime_annotations_are_compile_time_only` ——
    带标注与不带标注的等价函数返回完全相同的结果。
  - **误解**："`PhantomData` 里存了一个 `T`" → **实际**：它是单元结构体，没有字段，大小为 0。
    → **证据**：`tests/c04_lifetime.rs::phantom_data_is_zero_sized`。

- **对应实验**：[`c04_lifetime`](../../experiments/m1-ownership/examples/c04_lifetime.rs)

## 与后续学习的关联

FR-014 要求每项能力说明与后续 Linux / eBPF / Aya 的关联点，或显式标注为仅是基础。

| C-ID | 关联点 |
|------|-------|
| **C-01 Ownership** | 直接对应。Aya 用户态代码里，`Bpf` 对象、加载后的 program、pinned map 的**句柄**都是 RAII 资源：句柄销毁 = 程序卸载 / map 释放。搞不清所有者是谁，就会出现"程序刚加载就被卸载了"这类现象 —— 因为句柄在一个临时值里、语句结束就销毁了。销毁时刻由静态作用域决定这一点，在这里是**可预测**而非玄学。 |
| **C-02 Move semantics** | 直接对应。eBPF 的 packet buffer 视图（`&[u8]`）在解析器之间传递时，"移动 vs 借用"决定了能不能零拷贝。而 `Copy` 与 `Drop` 互斥这一条，在 Feature 003+ 设计 map 句柄类型时会直接用到：句柄必须 `!Copy`，否则同一个 fd 会被 close 多次。 |
| **C-03 Borrowing** | 直接对应，且是**理解 eBPF verifier 的最佳类比**。borrow checker 与 verifier 做的是同一类事：在**不运行程序**的前提下静态证明某类访问安全。二者甚至有相同的失败模式 —— 逻辑上安全但证明器推不出来，于是被拒绝。学会"编译器为什么拒绝我"这件事本身，比学会具体规则更重要。此外 `RefCell` 的运行期检查思路，与 BPF map 的并发访问模型（US4 会展开）同源。 |
| **C-04 Lifetime** | 直接对应。`XdpContext` 里的 `data` / `data_end` 指针只在**本次回调期间**有效，这在 Rust 侧正是一个生命周期约束；Aya 用生命周期参数把它编码进类型，使"把包指针存起来下次再用"变成编译错误。`PhantomData` 的零成本类型级区分，则是 Aya 区分 map 类型（`HashMap<K, V>` vs `PerfEventArray`）的手法。 |

四项都不是"仅为理解基础"—— 它们是本 Feature 里与后续耦合最直接的一组，
这也是 US1 被列为 FR-012 硬前置的原因。
