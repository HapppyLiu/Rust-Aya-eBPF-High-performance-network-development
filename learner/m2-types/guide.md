## 0. 开始之前

- **前置模块**：m1（C-01…C-04），当前验收状态：查 `acceptance/capability-matrix.md`。
- **本模块假定你已经能**：
  - 说出一个值的所有者是谁、哪一行发生了移动或借用（C-01 / C-02 / C-03）；
  - 解释生命周期标注约束的是检查器而不是值的寿命（C-04）；
  - 用 `size_of` 这类问题区分"编译期事实"和"运行期观察"。
- **本模块结束时你应该能**：面对一段混用泛型与 trait 对象的代码，**在不运行程序的前提下**
  标注每个调用点的分发方式（静态还是动态）、实际会执行哪个实现，
  并用布局断言和编译器中间表示核对标注是否正确。

**为什么排在 m1 之后**：抽象层的每个值仍然服从所有权与借用。
分不清"这个 `&dyn Trait` 借的是谁、活到什么时候"，后面读 Aya 的 map / program 句柄时
你会把"接口"和"句柄寿命"搅在一起。

## 1. 本模块你要能回答的问题

先自己答一遍，答不上来是正常的 —— 记下来，那就是你这个模块的学习目标。

### C-05 Struct / Enum

1. 一个 `struct` 的大小由什么决定？字段**声明顺序**会不会改变大小？如果会，凭什么？
2. 一个 `enum` 在内存里怎么同时装下"我是哪个变体"和"这个变体带的数据"？
   和 C 里"手写一个 tag + union"比，多了哪一条语言级约束？
3. 有些 `Option<T>` 和 `T` 一样宽，有些更宽。分界线在哪？这个现象对哪些 `T` 成立？
4. 判别式 + 变体共享空间这种布局，为什么在**没有 GC** 的环境里仍然可用？
   带 GC 的语言常用另一种 tagged 手法，差在哪？
5. `size_of`、`align_of`、`offset_of` 各自回答的是哪一个不同的问题？
   只知道大小、不知道偏移，会漏掉哪类错误？

### C-06 Trait

1. trait 更像 C 的函数指针表，还是更像 C++ 的抽象基类？这个类比在哪一点会骗人？
2. 同一个 trait，写成泛型参数和写成 trait 对象，调用时走的是同一条路径吗？
   如果不是，两条路径各自在**什么时候**选定实现？
3. 用 `size_of` 分别量一下"指向具体类型的引用"和"指向 trait 对象的引用"。
   它们一样宽吗？如果不是，多出来的那部分是什么？
4. `Display`、`Deref` 这类标准库 trait，调用看起来像格式化或自动解引用。
   编译器实际解析到哪一份实现？你怎么**自己**在源码里确认？
5. 什么情况下泛型写不下去、必须改用 trait 对象？这个限制来自类型，还是来自调用约定？

### C-07 Generic

1. 源码里一份泛型函数，编译之后对应几份机器码？谁决定份数？
2. 调用泛型函数时如果缺了某个 trait bound，编译器会拒绝。
   先写下你预测的**错误形态**（不要先编译再抄），再去跑实验核对。
3. 同一套逻辑，泛型版本和 trait 对象版本的**返回值**能一致吗？
   如果能，它们付出的代价分别在哪一侧（体积 / 调用 / 可扩展性）？
4. "单态化"三个字经常被当成优点。它在二进制体积上的代价是什么？
   什么时候这个代价会大到你愿意改用动态分发？
5. `Iterator` 和 `PartialOrd` 的 bound 写在函数的哪一侧？
   约束的是"入参能做什么"，还是"返回值是什么"？两者能互换吗？

### compile_fail 样本的写法

编译失败的样本放在 `experiments/m2-types/compile_fail/`，首行声明你**事先**预测的错误码：

```rust
//! EXPECT: <你预测的错误码>
//! CLAIM: <这个样本违反了哪条规则>
```

然后在 `tests/` 里用 `rf_harness::compile_fail::expect_errors` 断言。
**先写** `EXPECT` **再编译** —— 反过来就只是抄写编译器输出。

### 编译器行为观察（C-06 / C-07）

```bash
tools/emit-llvm-ir.sh m2-types --example c06_trait
```

在 LLVM IR 里找：静态分发的那次调用是**直接**的还是间接的；
动态分发的那次调用经不经过一张表。
IR 文本一律是 NON-ASSERTION —— 抄进 OBSERVATIONS，不要写进断言。

单态化实例数用 nightly 的打印开关观察（具体命令见 `predictions.md` #11）。
数出来的是观察值，不是稳定断言。

## 4. 提示阶梯

逐级往下看，每次只看一级。

### C-05 Struct / Enum

- **Hint 1（方向）**：不要先背"Rust enum 比 C union 安全"。先画一张字节图：
  哪几个字节表示"我是谁"，哪几个字节表示"我带着什么"。画出之后再问安全从哪来。
- **Hint 2（位置）**：对同一个 `struct` 调换两个字段的顺序，分别 `size_of`。
  数字变了就去问：对齐要求把空位插在了哪。
- **Hint 3（拆解）**：拆成两问 —— (a) `Option<&T>` 为什么有可能不增宽？
  (b) `Option<u8>` 为什么通常要增宽？把"值域是否用满"单独拿出来想。

### C-06 Trait

- **Hint 1（方向）**：先别想语法。问一个更基本的问题：
  调用方在**写出调用的那一行**时，知不知道被调函数的具体地址？
  知道，就是一条路径；不知道，就是另一条。
- **Hint 2（位置）**：`tools/emit-llvm-ir.sh` 导出 C-06 的 example，
  在 IR 里分别搜两个调用点。一个名字能对上具体类型，另一个对不上。
- **Hint 3（拆解）**：宽度差和调用方式是两件事。
  先用 `size_of` 量两种引用，再去 IR 里看调用指令。不要用其中一个去"证明"另一个。

### C-07 Generic

- **Hint 1（方向）**：把"一份源码"和"一份机器码"拆开。
  C 的 `int max(int, int)` 是一份对一份；Rust 的泛型函数不是。差在谁做了复制？
- **Hint 2（位置）**：用 nightly 的单态化打印开关跑 `c07_generic`，
  **数**出现了几次同一个函数名、后面跟了哪些类型。
- **Hint 3（拆解）**：缺 bound 的编译失败，和"运行起来结果不对"，是两类问题。
  前者发生在单态化**之前**（编译器还在选候选实现），
  后者发生在单态化**之后**（已经有一份具体机器码了）。你的实验分别落在哪一侧？
