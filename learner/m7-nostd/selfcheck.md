## 五项检验

- [ ] **1. 自述概念**

  向"懂 C 但没学过 Rust 的同事"解释本模块三项能力。规则：每冒出一个 Rust 术语，
  要么当场用 C 世界的话解释，要么换掉它。

  特别注意：
  - `no_std` —— 讲清关掉的是哪一类默认依赖，而不是"语言被砍掉一半"；
  - core / alloc / std —— 用"语言原语 / 堆上的集合 / 操作系统服务"来拆，不要三词循环定义；
  - 分配器 —— 讲清集合类型和"真正拿出一块内存的人"不是同一个角色；
  - panic —— 讲清没有操作系统时，这条路必须由你接住，而且不能从处理函数里返回。

- [ ] **2. 最小示例**

  为每个 Capability **默写**一段 ≤15 行代码。默写，不是复制。

  | C-ID | 要默写的东西 |
  |------|------------|
  | C-22 | 一个 `no_std` + `no_main` 的入口骨架（含你认为必需的处理函数） |
  | C-23 | 同一段求和的 **core 版**和 **alloc 版**签名（不必写满 std 版） |
  | C-24 | `GlobalAlloc` 的 `alloc` 骨架：从一块静态缓冲里切出满足对齐的区间（可用伪代码） |

- [ ] **3. 底层机制**

  说出编译器 / 运行时实际做了什么，**并指出你的依据来自哪个实验断言、哪次构建退出码或哪处源码**。

  1. 给 crate 加 `#![no_std]` 之后，为什么切片和 `Option` 往往还在？依据在哪？
  2. `std::vec::Vec` 的实现落在哪一层？你是在哪份源码里看到再导出的？
  3. 默认构建成功，证明的是"这个 target 上有堆"，还是"本 crate 提供了分配入口"？哪条命令或哪份源码支撑？
  4. 拿掉 panic 处理之后的那次失败，缺的是 core 里的函数体，还是消费方必须供给的语言项？依据？
  5. host 侧检查工具退出码 0，能不能写成"裸机产物没有未定义行为"？缺了哪一句范围声明？

  说不出依据的那条，标记为"待补"。

- [ ] **4. 常见误区**

  为 C-22、C-23、C-24 **各**说出至少 1 条**你自己曾经的**误解，以及推翻它的证据。

  从别处抄来的"常见误区"没有诊断价值。如果你真的一条都没误解过，
  那就去看 `predictions.md` 里 `一致? = ✗` 的那几行 —— 那就是你的误解。

  有一条误区本模块**强制**你处理：把 `no_std` 说成"不能用标准库"。
  用你自己的证据推翻它（源码属性、再导出、或某次构建的归属），不要背句子。

- [ ] **5. 验证性问题**

  回答下列问题。答案不在本文件里。

  1. 产物不能在本机执行。Independent Test 还过吗？本模块把"可运行"定义成什么？
  2. 一次构建里同时拿掉 panic 处理、引入 std 类型、再写 `Vec`。分母还能不能用"本次 stderr 有几条"来算？为什么清单要固定为 6 条、每步单独构建？
  3. `String` 失败和 `File` 失败能写成同一层吗？若不能，缝在哪？
  4. 已经 `extern crate alloc`，仍然链接失败。下一步该找 alloc crate 的源码，还是找本 crate 有没有注册全局分配器？
  5. 把静态数组 bump 分配器搬进后续那种没有堆、没有通用分配助手的受限环境，缺的是哪一类前提？本模块哪一句观察记录在划这条边界？
  6. `nm` 里没有 C 库启动例程，能不能推出"所以这是一个 Linux 用户态程序"？静态检查脚本实际在断言什么？
